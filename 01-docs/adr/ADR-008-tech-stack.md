## コンテキスト

開発ロードマップ P3 は、実装着手の前提となる言語・ソルバー・配布形態の決定を求めている。
判断材料は以下の 3 つである。

**(1) v1（shift-scheduler-claude）の教訓**

- v1 は React + Flask + PuLP(MILP) 構成のデスクトップアプリ（PyInstaller による単一 .exe 配布）
  として開発されたが、.exe 配布物が未完成（ダブルクリック起動が未達成）のままリリースブロッカー
  となった（ROADMAP 1.1 RB-3）
- フロントエンドテストの欠如が品質保証の穴となり、リリースブロッカーの一因となった

**(2) 技術調査の推奨（`01-docs/research/00-summary.md`）**

- 日勤のみのクリニック規模（数十名・1 ヶ月分）では MILP/CP-SAT で最適解を数秒で得られる
- 推奨順位: 第 1 位 Google OR-Tools CP-SAT、第 2 位 PuLP + HiGHS、第 3 位 Timefold（Java 前提）

**(3) 縦スライス実装の実績（PR #7）**

技術選定の妥当性を机上比較ではなく実装で検証するため、Python + OR-Tools CP-SAT による
最適化エンジンの縦スライスを先行実装した。結果は以下のとおりであり、推奨スタックが
本プロジェクトの要件（設定駆動・制約充足・性能）を満たすことが実証された。

| 検証項目 | 結果 |
|---------|------|
| ソルバー求解 | サンプル設定（スタッフ 5 名・1 週間分）で **OPTIMAL 解**を取得 |
| テスト | **6 件 PASS・SKIP 0 件**（config 読込・解の妥当性・HC-001〜004 充足検証） |
| カバレッジ | **91%**（scheduler パッケージ全体、pytest-cov 計測） |
| 実行時間 | テストスイート全体で約 4 秒（60 秒タイムアウト要件に対し十分な余裕） |

### 配布形態（Q-09: 仮デフォルト）

配布形態は REQUIREMENTS Q-09 の要確認事項であり、副院長の回答待ちである。
確認完了までの**仮デフォルトを「ローカル Web アプリ」**とし、実装はこの前提で前進させる
（回答待ちで停止しない。REQUIREMENTS 3.2 の設定駆動方針と同じ運用）。

仮デフォルトの根拠:

- v1 の .exe 配布（PyInstaller）は「ダブルクリック起動」が最後まで達成できず、
  リリースブロッカー RB-3 として残った。同じ手法の再採用はリスクが実証済みである
- ローカル Web アプリは Python 実行環境 + ブラウザのみで動作し、ビルド成果物の
  配布問題（ウイルス対策ソフトの誤検知・署名・サイズ）を回避できる
- v2 は管理者専用システム（スタッフ向け機能はスコープ外）のため、
  外部公開・マルチユーザー対応は不要であり、ローカル起動で要件を満たす

回答が仮デフォルトと異なる場合の影響は「結果と影響」節に記載する。

### フロントエンド方針（P3 では仮方針のみ）

- UI 技術の詳細選定は P4（アーキテクチャ設計）で行う。P3 時点の仮候補は
  **Streamlit**（Python 単一言語でUI構築可能・ローカル Web アプリと親和）とする
- v1 ではフロントエンドテストの欠如がリリースブロッカーの一因となったため、
  **テスタビリティを設計原則として確定**する:
  - UI 層とロジック層（最適化エンジン・設定読込）を分離し、ロジック層は UI なしで
    100% テスト可能に保つ（縦スライスの `02-src/scheduler/` は既にこの構造）
  - UI 層にも自動テスト（E2E 含む）を必須とし、テスト困難な UI 技術は採用しない
  - P4 の UI 技術選定では「自動テスト手段の有無」を必須評価軸とする

## 代替案と却下理由

| 代替案 | 却下理由 |
|--------|---------|
| PuLP + HiGHS（ソルバー） | 技術調査第 2 位。v1 資産の継続利用が利点だが、v2 は新規構築のため移行コスト優位性が消滅。ソフト制約の重み付け記述は CP-SAT の方が自然であり（`model.maximize()` で統一的に扱える）、P6 の目的関数実装（SC-001〜005）で差が出る。縦スライスで CP-SAT の動作実績も得られた |
| Timefold Solver（ソルバー） | 技術調査第 3 位。Java 21+ 環境が必須で、Python 版ラッパーは 2025-10 にアーカイブ済み。単一言語（Python）で完結できる構成を崩す理由がない |
| デスクトップ .exe 配布（PyInstaller 等） | v1 で「ダブルクリック起動」が未達成のままリリースブロッカー RB-3 となった実績。ビルド成果物の配布問題（誤検知・署名・サイズ）が Python + OR-Tools 構成では特に重い（ネイティブライブラリ同梱で肥大化） |
| ホスティング（クラウド公開） | v2 は管理者専用・単一施設のシステムでありマルチユーザー要件がない。スタッフの勤務データを外部サーバーに置くことは個人情報保護方針（ADR-007）上の追加リスクとなり、運用コスト（サーバー費・保守）も発生する |
| React 等の SPA フロントエンド | v1 で採用したが、フロントエンドテスト欠如の一因となった。管理者専用の小規模 UI に対して JS ビルドチェーンの複雑さが見合わない。Python 単一言語構成の方が保守性・テスト整備で優位（最終判断は P4） |

## 結果と影響

**ポジティブ**:

- P4（アーキテクチャ設計）・P5（スケルトン・CI 拡張）が本 ADR を前提に着手可能になる
- 縦スライス実装（`02-src/scheduler/`・`03-tests/`・`requirements.txt`）がそのまま
  本実装の基盤として継続利用できる（作り直し不要）
- 単一言語（Python）構成により、CI（lint・テスト・カバレッジゲート）の整備が単純化する

**ネガティブ・リスク**:

- 配布形態が仮デフォルトのため、Q-09 の回答次第で見直しが発生しうる。ただし影響は
  UI 層・起動方式に限定され、最適化エンジン・設定読込（本 ADR の中核）は配布形態に
  依存しない設計とするため、手戻りは限定的である
- ローカル Web アプリは「ブラウザで開く」操作をユーザーに求める。起動の簡便さ
  （v1 の .exe が目指したダブルクリック起動）はランチャースクリプト等で P7 までに解決する
- Streamlit が P4 のテスタビリティ評価で不採用となる可能性がある（その場合も
  Python 系 UI 技術から再選定し、本 ADR の言語・ソルバー決定は影響を受けない）

**P4 以降への設計指針**:

1. UI 層とロジック層の分離を維持する（ロジック層は UI なしでテスト可能）
2. UI 技術選定（P4）では自動テスト手段の有無を必須評価軸とする
3. 配布形態に依存しないエンジン設計とし、Q-09 回答による手戻りを最小化する

## 根拠

1. **実績ベースの確定**: 机上比較ではなく、縦スライス実装（PR #7）で
   OPTIMAL 解取得・テスト 6 件 PASS（SKIP 0 件）・カバレッジ 91% を実測した上での決定である
2. **技術調査との整合**: 5 領域並列調査（OSS・アルゴリズム・SaaS・ドメイン要件・学術文献）の
   第 1 位推奨（OR-Tools CP-SAT）と一致する
3. **v1 教訓の反映**: リリースブロッカー RB-3（.exe 配布未完成）・フロントエンドテスト欠如の
   再発を、配布形態の変更とテスタビリティ原則の明文化で構造的に防ぐ
4. **性能要件の充足**: 非機能要件「1 ヶ月分を 60 秒以内」に対し、縦スライス（1 週間分）は
   数秒で OPTIMAL 解に到達。日勤のみ・10 名以下の規模では CP-SAT の性能余裕が大きい
   （技術調査: 20〜50 名・1 ヶ月分でも数秒以内）
