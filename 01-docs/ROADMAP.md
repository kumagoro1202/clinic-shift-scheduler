## 1. 現状総括

### 1.1 v1（shift-scheduler-claude）で何が問題だったか

v1 は React + Flask + PuLP(MILP) 構成のデスクトップアプリ（PyInstaller による単一 .exe 配布）として開発され、ソルバー換装（HiGHS）や制約モデル刷新（Phase 0〜2）まで実施済みであった。しかし以下の問題により、v2 として作り直す判断に至った。

**(1) 勤務体系の前提が実態と乖離した（作り直しの直接原因）**

v1 は勤務体系マスタ（コード 001〜907、拘束10時間・休憩120分等のパターンを含む）を前提に構築された。その後、利用者から「9時間勤務・1時間休憩」の勤務形態へ変更したいという要望があり、前提となる勤務体系そのものが変わるため、既存実装の改修ではなく別リポジトリでの新規構築が選択された。

**(2) 7視点評価で特定されたリリースブロッカー（2026-02 実施）**

v1 の多角的評価（管理者/スタッフ/開発者/運用/経営/セキュリティ/法務の7視点）では、以下の5件が「リリース前に必ず解消すべき課題」と判定された。これらは v2 の要件定義に引き継ぐべき教訓である。

| # | 課題 | 深刻度 |
|---|------|--------|
| RB-1 | スタッフ向け機能（希望提出・シフト確認・交代申請）の完全欠如 | Critical |
| RB-2 | Excel出力・印刷機能の欠如（現場は紙運用が前提） | Critical |
| RB-3 | .exe 配布物の未完成（ダブルクリック起動が未達成） | Critical |
| RB-4 | 週法定労働時間（40時間）チェックの欠如 | Critical（法令違反リスク） |
| RB-5 | 36協定対応（時間外労働の記録・上限チェック）の欠如 | Critical（法令違反リスク） |

**(3) 技術面の知見（技術調査 2026-02 実施、`01-docs/research/` 参照）**

- 日勤のみのクリニック規模（数十名・1ヶ月分）では MILP/CP-SAT で最適解を数秒で得られる
- 推奨技術: 第1位 Google OR-Tools CP-SAT、第2位 PuLP + HiGHS、第3位 Timefold（Java 前提）
- 夜勤が存在しないため、夜勤インターバル・連続夜勤禁止等の制約は設計から完全に除外できる

## 2. 優先順位付き実行計画

### P1: 要求事項定義書（REQUIREMENTS.md）の作成

- **目的**: 9時間勤務・1時間休憩の新勤務体系における要求を確定し、以降の全作業の拠り所とする
- **作業内容**:
  - v1 の要求事項定義書・勤務体系マスタを参照しつつ、新勤務形態で維持する要件（リハ室・受付の人数制限、診療時間）と廃止する要件を仕分ける
  - v1 評価のリリースブロッカー5件（スタッフ機能・Excel出力/印刷・配布形態・週40時間チェック・36協定）を v2 要件として最初から組み込むか否かを明記する
  - 確認が必要な未確定事項（職種構成、休憩の取り方、土曜・水曜等の変則スケジュールの扱い等）を「要確認リスト」として整理し、要求提供者への確認に回す
- **完了条件**: `01-docs/spec/REQUIREMENTS.md` が PR マージされ、確定要件と未確定事項が区別して記載されている

### P2: 制約条件一覧（CONSTRAINTS.md）の作成

- **目的**: 最適化エンジンが守るべきハード制約（HC）・ソフト制約（SC）を要件から導出し、実装可能な形式で確定する
- **作業内容**:
  - 技術調査（`research/00-summary.md` 5章）の HC-001〜007 / SC-001〜007 を出発点に、P1 の確定要件に合わせて取捨・修正する
  - 各制約に ID・内容・優先度（ソフト制約は重み）・根拠（法令/運用要件）を付与する
- **完了条件**: `01-docs/spec/CONSTRAINTS.md` が PR マージされ、全制約に ID と根拠が付与されている
- **依存**: P1

### P3: 実装言語・技術スタック選定（ADR-008）

- **目的**: 実装着手の前提となる言語・フレームワーク・ソルバー・配布形態を決定する
- **作業内容**:
  - 技術調査の推奨（OR-Tools CP-SAT / PuLP + HiGHS）を軸に、v1 の教訓（.exe 配布の難航、フロントエンドテスト欠如）を踏まえて比較検討する
  - 配布形態（デスクトップ .exe / ローカルWebアプリ / ホスティング）はスタッフ向け機能（RB-1）の要否と密接に関わるため、P1 の結論と合わせて判断する
  - 決定を ADR-008 として記録し、CLAUDE.md の「言語別開発ルール」節を追記する
- **完了条件**: ADR-008 が Accepted となり、CLAUDE.md に言語別ルールが追記されている
- **依存**: P1（配布形態・スタッフ機能要件）

### P4: アーキテクチャ設計（ARCHITECTURE.md・外部/内部設計）

- **目的**: 実装全体の構造を確定し、以降の実装 PR を小さく分割可能にする
- **作業内容**:
  - `01-docs/design/ARCHITECTURE.md`（全体構成・データフロー）
  - `01-docs/design/external/`（画面設計・入出力設計。Excel/印刷出力を含む）
  - `01-docs/design/internal/`（データモデル・最適化エンジンのモジュール設計）
- **完了条件**: 設計文書一式が PR マージされ、実装タスクへの分割（実装順序リスト）が含まれている
- **依存**: P2, P3

### P5: プロジェクトスケルトン・CI 拡張

- **目的**: 言語決定後の開発基盤（ビルド・lint・テスト・カバレッジゲート）を整備する
- **作業内容**:
  - 選定言語のプロジェクト雛形を `02-src/` に配置し、`03-tests/` の unit/integration/e2e を実行可能にする
  - GitHub Actions に lint・テスト・カバレッジ 80% ゲートを追加する（既存の pii-check / pr-check と並列）
- **完了条件**: 空実装＋サンプルテストで CI が全て PASS する状態が main に入る
- **依存**: P3

### P6: MVP実装 フェーズA — 最適化エンジンコア

- **目的**: システムの中核価値である「制約を満たすシフトの自動生成」を最小構成で動かす
- **作業内容**:
  - スタッフ・勤務体系・診療カレンダーのデータモデル実装
  - CONSTRAINTS.md のハード制約・ソフト制約をソルバー上に実装
  - 1ヶ月分のシフト生成 CLI/API と、制約充足を検証する自動テスト（カバレッジ 80% 以上)
- **完了条件**: 匿名サンプルデータで1ヶ月分のシフトが生成され、全ハード制約充足がテストで検証されている
- **依存**: P4, P5

### P7: MVP実装 フェーズB — 管理者UI・出力機能

- **目的**: v1 リリースブロッカーの再発を防ぎ、現場運用（紙配布）に足る出力を最初のリリースに含める
- **作業内容**:
  - 管理者向け画面（スタッフ管理・希望休入力・シフト生成・結果編集）
  - Excel 出力・印刷レイアウト
  - 週40時間チェック・時間外労働の警告表示（法令面の教訓の反映）
- **完了条件**: 管理者がシフト作成月次業務を一通り実施でき、Excel/印刷出力が可能な状態
- **依存**: P6

### P8: 継続運用タスク（随時）

- **目的**: リポジトリの健全性維持
- **作業内容**:
  - dependabot が作成済みのブランチ（markdownlint-cli2-action v22/v23、actions/checkout v6）の PR 処理
  - README のディレクトリ構成記載と実体の乖離解消（P1〜P4 の文書追加に合わせて随時更新）
- **完了条件**: dependabot PR が全て処理され、README 記載と実体が一致している

## 3. 実行順序の考え方

```text
P1 要求事項定義 ──→ P2 制約条件 ──→ P4 設計 ──→ P6 エンジン ──→ P7 UI・出力
       │                            ↑              ↑
       └────→ P3 技術選定 ──┬───────┘              │
                            └──→ P5 スケルトン・CI ─┘
P8 継続運用（随時）
```

- P1 は要求提供者への確認事項を含むため、**最初に着手し確認待ち時間を先行して消化する**
- P3 は P1 の結論（配布形態・スタッフ機能）に依存するが、比較検討自体は P1 と並行で進められる
- P6 以降は 7ステップAI自律開発ワークフロー（`/workflow`）に沿って小さな PR 単位で進める
